# 运行记录与持久化设计草案

状态：讨论稿，尚未决定是否建立数据库表。07 区观测等级规则未验证，当前所有整晚结果均为 `INSUFFICIENT_DATA`，建议先不持久化每次查询，避免保存大量无法区分的兜底结果。本文先明确未来记录契约和需要决定的事项。

## 设计目标

未来若要追查一次判定，需要能够回答：当时评估的是哪个地点和本地日期、运行了哪个规则版本、每个输入来源返回什么状态和时间范围、最终结果与原因是什么。记录必须与接口 DTO 解耦，避免 DTO 字段改动直接成为数据库迁移。

## 候选记录

### `evaluation_run`

一行代表一次用户触发的评估请求，候选字段：

- `id`：不可预测的运行标识。
- `created_at_utc`：运行时间。
- `rule_version`、`rule_status`：规则版本及验证状态。
- `location_ref`：首选已选地点的地理编码 ID；默认不保存自由输入文本或精确坐标。
- `requested_local_date`、`timezone_id`：当地日期与 IANA 时区。

### `evaluation_night`

每个评估运行对应一个或多个夜晚，候选字段：

- `run_id`、`local_date`、`window_start_utc`、`window_end_utc`。
- `level`、`reason_code`。
- 若未来规则输出证据，证据应引用输入快照或来源记录，而不是只存渲染后的说明文字。

### `evaluation_source`

每个运行、每个输入来源一行，候选字段：

- `run_id`、`source_key`、`fetch_status`、`time_scope`、`failure_code`。
- `retrieved_at_utc`、`source_observed_at_utc`、`source_forecast_at_utc`、`scope_start_utc`、`scope_end_utc`。
- `source_url` 只用于出处，不作为可复现快照的替代。

此结构对应当前 `ObservationFactsResponse` 的事实边界，但不是最终 schema。完整原始响应可能较大，且需要核对保存许可、费用和清理成本；若不保存原始输入或足够的结构化快照，旧运行只能追溯来源状态，不能保证重算出相同结果。

## 隐私和范围边界

- 当前没有用户账户；Agent 对话是否保存为跨会话历史尚未决定，因此本草案不设计用户资料表或聊天正文存储。
- 地点 ID、日期及时区仍可能暴露查询习惯；没有用途和保留期限前，不开启长期记录。
- 失败记录也可能包含输入参数；日志和数据库均不得保存不必要的自由文本或精确坐标。
- 当前缓存继续使用内存，不为短时缓存创建 Entity 或 Repository。

## 建表前需要定下来的决策

1. 运行记录是否服务于故障诊断、规则评估，还是两者都需要？
2. 查询地点标识和来源快照分别保留多久？何时及如何删除？
3. 是否保存完整来源输入以支持重现，还是接受只能审计状态、不能重算旧结果？
4. 是否需要用户身份关联？当前产品流程没有登录，不建议为此提前加账户系统。
5. 部署所用数据库、迁移工具、备份和访问策略是什么？

## 当前结论

在 07 区规则未验证、运行记录用途和保留策略未确定前，不建立数据库 schema，也不将每次查询写入持久存储。上述字段仅作为评审起点；产品确认用途与保留策略后，再设计迁移、Entity、Repository 和集成测试。
