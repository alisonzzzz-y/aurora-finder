# Phase 0: source and rule review

Review date: 2026-09-24. This is a record of a few direct samples and provider documentation, not approval of the whole data pipeline.

| Area | Confirmed so far | Still required before viewing advice |
| --- | --- | --- |
| NOAA OVATION | Direct samples returned `Observation Time`, `Forecast Time`, `Data Format`, and 65,160 `[longitude, latitude, aurora]` points. Longitudes were 0–359 and latitudes -90–90. Three samples five minutes apart changed ETag, Last-Modified, observation time, and forecast time. | Define freshness from both timestamps. Validate coordinate wrapping and map rendering at the longitude seam, in both hemispheres. Continue monitoring failures before making long-term availability claims. Do not treat cell intensity as a user's sighting probability. |
| NOAA Kp | A direct sample contained objects with `time_tag`, `kp`, `observed`, and `noaa_scale`. The status values included `observed`, `estimated`, and `predicted`. NOAA's three-day forecast labels its Kp slots in UTC (`00-03UT` through `21-00UT`); JSON `time_tag` values match the start of those slots but omit an offset, so the provider parses them as UTC. | Confirm long-term cadence, stale-data handling, and the official operational date range from repeated samples. Keep past observations, estimates, and future predictions separate. Kp is a geomagnetic trend, not a location-level visibility forecast. |
| Global Kp activity badge | NOAA's aurora viewing guide describes Kp 0–2 as dim and quiet, 3–5 as brighter/more active, 6–7 as bright/active, and 8–9 as very bright/active. The UI groups these source-described ranges into low (<3), medium (3–<6), and high (>=6). | These labels summarize global geomagnetic/auroral activity only. They do not estimate whether aurora is visible from a selected place and do not replace cloud, darkness, and local viewing-rule validation. |
| MET Norway clouds | The official data model lists `cloud_area_fraction` in percent in `instant.details`, with global forecast coverage. Terms require a real identifying User-Agent, attribution, coordinate rounding to at most four decimals, and cache behavior based on response headers. | Obtain a genuine contact URL or address for the backend User-Agent. Then sample northern Europe, Ireland, and a southern location from the local machine and deployment host; inspect field availability, timestamps, cache headers, 203/403/429 behavior, and forecast gaps. No weather request has been made as part of this scaffold. |
| Place search and time zone | Open-Meteo returned usable records for Tromsø (Europe/Oslo), Galway (Europe/Dublin), Ushuaia (America/Argentina/Ushuaia), Apia (Pacific/Apia, longitude -171.77°), and Longyearbyen (Arctic/Longyearbyen). Non-city gazetteer features also appear, including Mount Everest (`MT`) and Svalbard Archipelago (`ISLS`). Its free API is non-commercial and requires CC BY 4.0 attribution. | This is name search over indexed places, not arbitrary-coordinate/time-zone lookup. Search results can be surprising: `Mount Everest` returned a same-name South African mountain before Nepal, and `Svalbard` returned an Icelandic `Svalbardseyri` before Svalbard features. Keep explicit selection; display country, administrative area, coordinates, and time zone so users can distinguish matches. Add caching and rate control. Replace the provider if the use falls outside the free terms. |
| Darkness | IANA time zones can produce the three local calendar dates after a place is selected. The Apache-2.0 Java library `commons-suncalc` is a candidate for local solar-position calculations; NOAA publishes an independent solar calculator and defines astronomical twilight at a solar elevation of -18°. | Compare the candidate's solar elevations with NOAA at ordinary and high latitudes before adopting it. Define the product's darkness threshold for unaided-eye viewing; the -18° astronomy definition is not automatically the viewing rule. Test continuous daylight, continuous darkness, midnight crossings, daylight saving changes, and the date line. A sunrise/sunset-only shortcut is insufficient at high latitude. |
| Viewing levels | The product will use high, medium, low, and insufficient-data labels for unaided-eye viewing. | Establish a versioned rule from verified examples and official guidance. Define source freshness, valid forecast windows, cloud aggregation over dark hours, missing/conflicting data handling, and what each level means. Until then all API nights return `INSUFFICIENT_DATA`. No percentage probability is computed. |
| Agent | Planned tools are read-only and must share the backend's facts and rules. | Decide the model, cost limit, privacy and retention policy, tool trace storage, and evaluation cases before enabling questions. |

## Direct sample details

- The OVATION response sampled on 2026-09-24 reported observation time `2026-09-23T18:55:00Z` and forecast time `2026-09-23T20:26:00Z`. This is one snapshot, not a measured refresh interval.
- Three auditable OVATION samples were fetched from the official JSON endpoint at `2026-09-24T11:50:00Z`, `11:55:03Z`, and `12:00:10Z`. Each returned HTTP 200 and 65,160 grid points. In order, `Last-Modified` was `11:48:44Z`, `11:51:21Z`, and `11:56:35Z`; observation times were `11:41Z`, `11:43Z`, and `11:48Z`; forecast times were `12:49Z`, `12:54Z`, and `13:00Z`. ETag and content SHA-256 changed at each sample. Compressed raw responses and the hash manifest are in `docs/data/noaa-ovation-samples/`; hashes were checked against decompressed bytes. This ten-minute observation shows updates during that window only, not a guaranteed cadence or availability SLA.
- The Kp response sampled on 2026-09-24 covered `2026-09-16T00:00:00` through `2026-09-26T00:00:00`, with 62 observed, 2 estimated, and 17 predicted entries.
- The NOAA official three-day text product uses `00-03UT`, `03-06UT`, and subsequent three-hour UTC slots. The JSON timestamp has no offset suffix; the Kp provider normalizes it as a UTC period start, preserves `observed`/`estimated`/`predicted` as a constrained enum, and returns its own retrieval time separately. This convention is supported by the official product's UTC labels and matching JSON samples; it does not establish a refresh SLA.
- The homepage's global activity badge uses Kp bands `<3`, `3–<6`, and `>=6`, grouped from NOAA's aurora viewing guide ranges. It is explicitly labelled as global activity, not local visibility or viewing probability. Shared backend Kp responses are cached for five minutes; this operational cache interval is not a NOAA freshness guarantee.
- Open-Meteo returned `Europe/Dublin` for Dublin, Ireland, and `America/New_York` for Dublin, Georgia. The `/v1/get?id=...` endpoint returned the selected record.
- Open-Meteo geocoding was queried directly on 2026-09-24 with `count=5&language=en&format=json`. `Tromso` returned one Norwegian record named `Romssasuolu`, with `Tromsø` as admin2 and `Europe/Oslo`; `Galway` returned Galway, Ireland first (`Europe/Dublin`) and other same-name matches; `Ushuaia` returned Argentina (`America/Argentina/Ushuaia`); `Apia` returned Samoa (`Pacific/Apia`, longitude `-171.76666`); and `Longyearbyen` returned Svalbard (`Arctic/Longyearbyen`). `Mount Everest` returned three `MT` records, with South Africa before Nepal; `Svalbard` included a `ISLS` Svalbard Archipelago record after an Icelandic name match. `zzzxqv-unmapped` and `zz` returned empty result lists.
- Open-Meteo's current docs specify name/postal-code search, exact matching for two-character names, normalized prefix matching for names of three or more characters, and no results for empty or one-character searches. A country/admin1 qualifier must match exactly. This interface does not accept arbitrary coordinates as a substitute for place selection.
- On 2026-09-24, application-level geocoding controls were added: normalized searches are cached for 10 minutes, location records for 1 hour, and identical concurrent misses are coalesced. The process-local safety budget is 500 calls/minute, 4,500/hour and 9,000/day, below the published free limits; failed calls are not retried automatically. A horizontally scaled deployment must share or partition this budget.
- The local shell could not resolve the provider host inside its network sandbox. Direct samples were fetched with approved network access. The locally running backend successfully searched Dublin and loaded its selected record. Backend access from a planned deployment has not been checked.
